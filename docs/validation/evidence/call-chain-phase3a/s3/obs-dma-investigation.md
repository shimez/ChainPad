# S3：OBS Ready共存負荷の内部DMA割当失敗（既存証拠による調査）

対象は正式版 `v0.13.0` と候補 `f78d912` の通常S3。実機への問い合わせ・再試験・再ビルドは行っていない。**OBS Disabledの独立2起動ゲートはPASS、OBS Ready共存負荷の割当失敗増分0条件はFAIL**。以下の要因帰属は、その判定とは別である。

## 1. 失敗時に確定できること

`src/diagnostics.cpp::allocationFailed` は、要求に渡された**同じcaps**で総空き・累積最小空き・最大連続空きを問い合わせる。SDK `esp_heap_caps.h` により `0x80c = INTERNAL (0x800) | DMA (0x008) | 8BIT (0x004)`。すべての条件を満たす内部ヒープ領域が対象で、任意の内部RAMやPSRAMの総空きではない。通常のPSRAMへこの要求をそのまま逃がすことはできない。

| フック記録（B） | 要求 | 同caps総空き | 累積min | 同caps最大連続 | 要求に足りない連続長 |
|---|---:|---:|---:|---:|---:|
| 1 | 1,626 | 3,248 | 1,812 | 948 | 678 |
| 2 | 1,521 | 3,216 | 1,812 | 948 | 573 |

**確定**：各要求より総空きは大きいが、1ブロックとして取れなかった。複数ブロック／領域に分かれた空きと一時的な占有で説明できる。永続的なリーク、特定の断片化原因、2件が同一パケットの再試行だったことは示さない。`phase=loop` はsetup後の大区分でタスク名ではない。`heap_caps_malloc` はAPI名で呼出元PCではない。

**有力な推定**：ネットワーク側のフレーム用確保。約1.5–1.6 KiBと内部DMAの組合せに整合する。組み込まれるArduino `WiFiGeneric.cpp` は既定の非staticモードでWi-Fi初期化に動的TXバッファ設定を渡す。C5の[別診断](../../call-chain-c5-phase2d/comparison/README.md)では、同種の失敗を正しいリビジョンのROMで `esf_buf_alloc_dynamic` に帰属できた。**S3のPCは採れていない**。TCPの設定GET送信、UDPのOSC送信、OBSのWebSocket、制御/受信側をサイズだけで選別できない。S3でC5と同じ関数・同じ方向だったとは言えない。

**区別すべき間接要因**：`src/osc_backend.cpp` のOSCエンコード配列はスタック。Arduino `NetworkUdp.cpp` の送信作業領域は通常の `malloc(1460)` で、今回の要求サイズ・API指定そのものではない。S3のGET用 `JsonDocument`、シリアライズ用 `String` もこの3種のcapsを明示しない。ただし共用可能な内部領域を先に占有し、後続DMA要求の連続余裕を削る可能性はある。パケットのpayload長からドライバ確保サイズを逆算はできない。

## 2. 実測の境界と未測定区間

単位B。内部欄は `INTERNAL|8BIT` の **free / minFree / largest**。DMA欄は別途取得した `0x80c` のlargest。診断中の各問い合わせも同時ではない。

| 候補・採取点 | 内部 free / min / largest | DMA largest | PSRAM free | 失敗 |
|---|---|---:|---:|---:|
| Disabled起動1、224保存直後（installed） | 44,000 / 22,888 / 24,564 | 31,732 | 8,297,028 | 0 |
| 同、初回読戻し後 | 46,552 / 13,840 / 31,732 | 31,732 | 8,297,028 | 0 |
| 同、単独GET 1回目後 | 46,524 / 13,840 / 31,732 | 31,732 | 8,297,028 | 0 |
| 同、3回目の保存→GET後 | 46,584 / 9,548 / 31,732 | 31,732 | 8,297,028 | 0 |
| Disabled起動2、永続化確認後のpre | 49,968 / 18,724 / 31,732 | 31,732 | 8,297,028 | 0 |
| 同、3回目の保存→GET後 | 46,540 / 13,912 / 31,732 | 31,732 | 8,297,028 | 0 |
| Ready、別試行のRotation 3出力直前（224件ではない） | 43,584 / 19,736 / 31,732 | 31,732 | 8,297,028 | 0 |
| Ready、今回の224件保存＋読戻し後、並行負荷直前 | 数値未保存 | 数値未保存 | 数値未保存 | 0確認 |
| Ready、並行負荷終了後の診断 | 41,600 / 6,824 / 31,732 | 31,732 | 8,297,028 | 2 |

Disabledの全行は[ゲート記録](candidate-gate.json)。Readyの最後のPSRAMは `allocated=89,092, minFree=8,279,480, largest=8,257,524`。loopTask / OBS workerのstack low-waterは4,192 / 3,172 Bで、いずれも**失敗瞬間のスタックではない**。失敗フックのmin=1,812と境界の内部min=6,824も対象capsが違う。PSRAM全体の不足を示す記録はない。

今回のランナーでは `pre` と `pre2` の診断は成功したが、後診断のassertが結果ファイル書込みに先行した。Ready条件の**保存直後と単独GET直後を分けた数値、並行送信中の時系列、各失敗とGET・OSCの時刻対応は未測定または未保存**。保存後のGET一致と直前failures=0から、失敗をその保存自体に帰属させない。後診断までにはtrigger HTTP、GET、OSC、status HTTP、診断も含まれる。208件の受信・GETの重なり幅は未確定。DisabledゲートとReady負荷ではfixture・通信量・起動履歴も異なり、表の差を「OBSだけの使用量」と引き算できない。

## 3. 配置と正式版からの差

| 領域 | 正式版 → 候補、S3での意味 |
|---|---|
| Engine | 正式版の実機 `sizeof(Engine)=1,580` → 候補ELF/mapの内部 `.dram0.bss` **9,548**、**+7,968 Bの常駐差**。候補は296 B×32のInvocation（9,472 B）を内蔵。親Call・Loopの復帰情報とFIFO管理を保持する。未使用枠やCallなし設定でもこの差は残る。個別のCall実行が今回のmallocを呼んだわけではない。 |
| 設定 | 両版ともS3のactive Configは明示的な `SPIRAM|8BIT` 確保。正式版診断のAction/Chain/Configは352/5,636/82,648 B、候補ELF型情報では352/5,636/82,652 B。`loopReachable` によるConfigの4 B増は外部側。候補は保存前検証にローカルなCallグラフを追加するが、GET中の常駐バッファではない。 |
| OBS | S3は両版とも受信組立を静的に内部配置。候補mapの `assemblyStorage` は `0x4010`（16,400 B）。**Disabledでもこの領域は解放されない**。workerスタック8,192 Bとキューも静的。Ready時は接続・ハンドシェイク・フレーム処理・TCP/WebSocket等の動的負荷が加わり得るが、OBS専用動的領域の差分は未測定。 |
| JSON / HTTP | `src/main.cpp` の `/api/config` は両版とも全レコードを事前検査し、再エンコードしながらchunk送信。全224件分のJSONを一括保持する方式ではない。S3の各レコードの `JsonDocument` と `String part` は既定アロケータ。各実体の内部／外部比、最大生存量はS3未測定。正式版との差分にC5専用アロケータがあるが、S3では有効でない。 |
| BLE | `platformio.ini` のS3通常設定は両版とも `CONFIG_BT_NIMBLE_MEM_ALLOC_MODE_EXTERNAL=1`。対応するNimBLEホスト確保を外部に置く設定で、BLEコントローラ・タスク・すべてのキューが外部にある証明ではない。BLE・USB別の占有量は未測定。 |

**比較の手掛かり**：同じ3出力Rotation試験の開始境界（OBS Ready）で、正式版の内部freeは51,940 B、候補は43,584 B（候補が8,356 B少ない）。両者とも内部largest=31,732 B、PSRAM free=8,297,028 B。Engine常駐増と方向・規模が合うが、別起動の境界であり因果の実証ではない。正式版にはDMA largest専用診断行がない。**正式版で今回と同一の224件・OBS Ready・GET＋OSC負荷は未測定**。候補の回帰か、正式版でも起きる余裕不足かは未判定。

**C5から移せる候補（未実装）**：①InvocationプールのみPSRAM化（候補S3内部の9,472 Bが対象）、②GET用 `JsonDocument` の明示PSRAM化（`String`・転送バッファは別）、③OBS受信組立16,400 BのPSRAM化。①は版差仮説、③は大きい固定占有、②はGET時の一時占有をそれぞれ単独に検証できる。C5では[①＋②でも失敗が残り](../../call-chain-c5-phase2d/plan-ac/README.md)、[③追加後に所定ゲートが合格](../../call-chain-c5-phase2d/assembly-stage1/README.md)した。S3で同じバイト数の連続DMA空きが増える保証はない。試すならPSRAM初期化時期、失敗時に内部へフォールバックしない設計、Wi-Fi/USB DMAに外部ポインタを渡さないこと、worker・実行タイミングへの影響を別途確認する。

## 4. 次に承認を求める検証（未実施）

1. **先に証拠を失わないランナーへ**。全生電文と単調時刻、各trigger、GET開始/終了/全内容一致、診断原文を逐次flushし、件数・割当失敗のassertは記録後。全試行で同じプログラムを使う。診断の頻繁なHTTP/CDC送信自体も負荷になるため、負荷中にポーリングを追加せず境界に固定する。
2. **候補と正式版の通常イメージでA/B**。新規書換え承認が前提。同一個体・PC・AP・OBS、同じUSB/BLE購読、同じ速度・文字列長・順序のCallなし224件（208 OSC＋16 Wait）、同じ起動後準備・保存履歴を使う。Disabled/Readyそれぞれ、保存→静止、単独GET、OSCのみ、GET＋OSCを別区間で採る。必要なら独立起動で順序差を排除する。正式版にもある失敗フックと内部/PSRAM値・stack・設定一致・受信列が共通の判定軸。正式版の平時DMA largestは欠測とし、失敗すればフックの同caps値を比較する。最初の新規失敗でその試験を停止・保存し、次の条件へ自動進行しない。
3. **通常版で分かる上限**：`m/h` と失敗フックで区間・caps・要求サイズ・失敗時largestまでは分かる。既存フックは総件数と先頭4件を保持し、タスク・呼出元・時刻・成功した一時割当は採らない。既存の追加診断出力も時間・メモリを消費する。失敗を再現した版を主証拠とし、成功1回だけで解消と判定しない。
4. **必要な場合のみ別承認の診断版**。まず失敗時に固定長の事前確保リングへ時刻・タスク識別・実際の要求元PCを最小限記録し、GETの事前検査/送信・OSC dispatchの境界と突き合わせる。フック内の直接の戻り番地だけではアロケータ内部を指し得るため、対象SDKの呼出経路で採取位置を検証し、同一S3 ELF/map・対応ROMリビジョンでオフライン解決する。フック内でprintf・動的確保・ネット送信はしない。必要時に限りGETのJSONとStringの配置・生存量を別計測する。リング・コード・採時・フックでBSS/配置・タイミング・断片化が変わり、現象を隠す／増幅する。診断版成功は通常版FAILを覆さない。
