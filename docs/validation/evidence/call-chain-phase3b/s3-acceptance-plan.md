# 3B-3：S3実WebUI受入手順（初回候補）

> 初回候補の承認済み手順。編集時拒否・代替先選択は旧方式。最終仕様と受入結果は[Phase 3B最終判定](s3-acceptance-results.md)を参照。

対象は `6367807` の通常S3アプリ。ローカルで確認済みの[選択欄](target-picker/README.md)を実機配信ページで確認し、[3AのWebUI残件](../call-chain-phase3a/phase3a-review.md)を判定する。以下は試験予定で、実機結果ではない。

## 準備済み・開始条件

- 通常ビルドの `firmware.bin` は1,739,072 B、SHA-256 `eda80a7514aaf99c04128dc950e6e07505a052067e0990d3c1f5228a298e6cbe`。`tests/check_image.py` でアプリ配置、S3識別、8 MiB、USB記述子を確認。書込み用にはこのアプリ単体をGit外に固定した。
- Git外の今回専用フォルダーに `ui-base.json`、`full-range.json`、`key-range.json`、`key-cycle-at-key1.json`、`key-valid.json` を生成。実UIと同じモデルで正常なFull、ID 28のFull/Key拒否、KEY1へKeyを合成した場合だけ生じる循環、KEY5へ正常貼付した絶対ID 25をオフライン確認済み。fixtureはWait・Loop・Callのみ。ベースFullは試験用OSC設定も含むので、初回保存は退避照合後のみ。
- Chrome、OBS Studio、旧8 MiBバックアップと両抽出物の整合性をPC上で確認。旧バックアップは比較資料であり、現在の実機を読んだことにはしない。実施時は実機のURLへ直接接続する（fixtureサーバー、リクエスト置換、キャッシュ済み旧ページは使わない）。保存操作の担当ブラウザーは常に一つとし、利用者の手動試験は自動試験と交互に行う。

## 実施承認後：退避・書込み・復元

1. 通常起動でUSB物理位置・機種・版、status/config/capabilities/OBS設定、保存・入力ready、接続・稼働・押下状態をGit外に記録。PCのOBS起動状態、プロファイル・シーンコレクション・現行シーン・出力状態も控える。前回の `v0.5.3` から相違があれば停止して復元基準を確認する。
2. 操作依頼時のみ、USBを抜かずBOOTを押したままRESETを押して離し、BOOTを離す。ポート番号だけで判断せずUSB物理位置・チップ識別/MAC・8 MiBを照合。今回は改めて8 MiBを**新しいファイル**へ退避し、64 KiB×128区間の実Flashダイジェストと全体を照合。partition tableから元factory (`0x10000`, `0x600000` B) とLittleFS (`0x630000`, `0x1d0000` B) を確認・抽出し、全体の該当スライスと照合。旧退避物は上書きしない。
3. 復元可能と確認してから、承認済み手順（no-reset、容量明示、進捗描画なし）でアプリ単体を `0x10000` に書き実Flashと照合。LittleFS不変を確認。案内後に**BOOTなしでRESET**。候補版・元設定の引継ぎと、実機配信HTMLに新しい選択欄があることを確認して試験開始。
4. 終了時は試験前と同じ個体を再同定し、今回退避したfactoryとLittleFSだけを全長復元。**両方の実Flashダイジェスト一致後**に通常RESETを依頼。NVS・ペアリング等は書き換えない。元版、全設定・capabilities・OBS設定、Wi-Fi/USB/BLE、入力ready・全解放・稼働0とPC側の元状態を照合（旧版で必要なら空Chainで受付確認）。OBS側の試験資産のみ片付け、起動した試験用OBSのみ通常終了。機密設定・識別子・生ログはGit外。

## UIの客観試験と合格条件

実ブラウザーでベースFullをImport・明示保存した後、別入力に未保存Waitを追加する。各拒否直前・直後で、全編集データとdirty、選択中の入力・行、表示値と要約、実機の独立GETによる全設定を比較。ブラウザーのネットワーク記録で保存トランザクションが開始されないことを確認する。読取り・statusポーリングは書込みに数えない。

| 操作 | 確認内容 |
|---|---|
| KEY1 PressのLoop内Callを開く | 自分以外の27件に対し、ID・グループ・イベント名・空表示を編集データと照合。既定の空のEncoder CCWを選択可。狭幅375 CSS pxと通常幅で選択欄・折り畳み要約を確認。 |
| `full-range` を全体Import、`key-range` をKey Import | それぞれID 28を拒否。エラーが対象を示し、編集データ・dirty・実機設定が不変。 |
| KEY1へ `key-cycle-at-key1` をImport、続いて既存Callの先をKEY2 Pressに変更 | 0→2→1→0を別々に拒否。既存Callの旧選択値・要約・Loop位置と別入力の未保存値を保持。 |
| KEY1のWait→Call | 既定先1→0のため元Waitを保ったまま有効な候補を表示。キャンセルで不変。再度選び直して空の25を指定し、確定・要約更新・編集継続を確認。 |
| KEY5でKey Import | 説明を読み、`key-valid` を選ぶ。KEY5 Pressで元の25（Encoder Push Release）を指し、未保存と表示。Loop内Callも空の26へ正常変更。明示保存後に別ページから再読込みし、予定した全変更（別入力のWaitを含む）と絶対IDが一致すること。 |

最初のclean状態でも循環拒否またはキャンセルを1回行い、未変更がdirty化しないことを別に記録。API拒否については3Aの証拠を参照し、今回は**UIの拒否・編集保護**を独立判定する。

## 利用者が評価する操作（後日、試験側がベースを用意してから）

1. PCでKEY1 PressのLoopを開き、Call欄の3見出しと空表示を確認。矢印でEncoder CCWからCW、Push Releaseへ移り、意図した先が分かるかを見る。
2. KEY2 Pressを選んで循環を起こし、理由・行番号・元の値を見て操作を続けられるか確認。冒頭のWaitをCallに変え、代替欄で一度キャンセル、次に空の先を選んで「完了」。要約だけで先が分かるか確認。
3. KEY5の `…` → Preset Import の説明を読み、渡された `key-valid.json` を選ぶ。予想した先と実際の表示を比較。保存は試験担当と合図して一度だけ行う。
4. 同じLANの手元端末が使えれば縦画面でネイティブ候補を実際に開く。見出し・長い項目・折返し・タップ・フォーカス復帰・拒否理由の見つけやすさを「問題なし／要調整＋操作手順」で記録。端末がなければPC狭幅の結果と区別してタッチ評価は未確認とする。

## OBS一覧（出力制御は実行しない）

試験用シーンコレクションに少数の既知名を用意し、空シーン、通常シーン、音声入力、無音メディア、Groupとその子を区別する。独立したPCのOBS WebSocketクライアントを使い、同時期のコレクションを照会。UIで各Actionの一覧を開き「更新」し、表示・本体一覧APIの状態/complete/generationと、別経路のOBS応答を採取する。本体APIを正解表にはしない。

- シーンは `GetSceneList`、入力は `GetInputList` にメディア対応／音声能力を照合して対象を揃える。Groupは `GetGroupList`、親別項目は `GetSceneItemList`／`GetGroupSceneItemList`。表示名の集合、親と項目IDの対応（UIが表示しないIDは選択後の編集値）を比較。順序に依存しない。
- 空シーンの項目がready＋completeで0件であること、項目を1件追加→更新→削除→更新し差分が双方で反映されること。OBS Disabledまたは未Readyの表示と空の正常結果を区別。一覧取得後は再取得しないまま60秒の鮮度期限を越え、古い候補を完全な現行一覧として扱わず、再更新で一致に戻ることを確認。取得打切り・期限切れ・エラーは空一覧PASSにしない。
- 不一致・誤保存・設定消失・対象不一致があれば後続試験を止め、操作列、初期・期待・実測、影響範囲、修正案と復元状況を記録。承認なく修正しない。OBS操作25件、他機種の一律回帰、STA／同一起動内USB再列挙は実施しない。
