### 履歴成功・失敗の検証方法

公開先は変更せず、実機から読み込んだページの外部取得先だけをブラウザ内で一時的に差し替えました。
本体APIは実機のままです。成功データは既存CHANGELOGに検証用0.10.0〜0.13.0節をメモリ上で加え、
製品と同じPython生成処理で作成し、ローカルHTTPサーバーからCORS取得しました。
正式未公開版の情報ではなく、画面内にも検証用データと明記しました。

| 条件 | 結果 |
|---|---|
| 履歴成功 | 初期折りたたみ、0.13／0.12／0.11の3件、残り0.10をユーザー操作で展開 |
| 取得失敗 | 履歴の取得失敗案内とReleasesリンク。通知・Installer維持 |
| 5秒タイムアウト | 読込中も編集値・本体情報更新を保持。タイムアウト後に失敗案内 |
| build/historyコミット不一致 | 履歴本文を表示せず、通知・Installer・Releases案内を維持 |
| 保存 | 成功状態、取得失敗後、タイムアウト中に通常の28 Chain保存・適用に成功 |
| 最終保持 | 全試験後のconfig／OBS設定が書き込み前の正規化JSONハッシュと一致 |

試験後はページを再読込して外部取得先の差し替えを除去しました。
検証用表示は残っていません。実機には検証ビルドが残っています（表示バージョン0.9.0）。

### 保存時の単発事象

最初の履歴成功状態での保存は、`/api/config/chain?token=1&input=22`が約10.1秒後にHTTP 502となり、
ブラウザ側では空レスポンスのJSON解析エラーで停止しました。commit送信前でした。
本体の設定と編集中のChainsは一致したままで、再起動も観測していません。

その後は、履歴取得を止めた状態、履歴失敗状態、タイムアウト中、履歴成功状態の順で
4回の保存が成功しました。履歴取得は最初の失敗時点では完了済みでした。
502の発生箇所が通信経路・ブラウザ接続・本体のどこかは特定できておらず、
今回の変更による回帰とも、無関係とも断定しません。リリース判断時に考慮すべき観測事項です。
