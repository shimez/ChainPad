# Configurator更新通知の変更履歴データ

## 実装状況

Phase 1〜3：CHANGELOG整理、生成・検証、Actions統合、Configurator表示まで実装済み。
総合テスト・4機種ビルド・実機確認はPhase 4で行います。実装段階ではタグ作成・公開は行いません。

## 情報源と記載方法

唯一の情報源はリポジトリ直下の`CHANGELOG.md`です。
正式リリースタグ間の差分を基準に、各版に次の2分類を記載します。

```markdown
## 0.10.0

### 追加機能
- 利用者向けの短い説明（機種限定ならS3／C5／C6などを明記）。

### 修正・改善
- なし

### 補足
検証記録や開発上の事情。表示用JSONには含まれません。
```

- 空欄にせず、変更のない分類は`- なし`と明記します。JSONでは空配列になります。
- 空行、CRLF、インデントによる箇条書きの折り返しを許容します。折り返しは空白で連結します。
- 箇条書きは`-`または`*`を使用できます。入れ子のリストやコードブロックは表示対象の分類では使用しません。
- 本文はプレーンテキストとして扱い、インラインMarkdownは解釈しません。
- その他の`###`分類は表示対象外です。`## Unreleased`は未公開メモとして使用でき、出力しません。
- バージョン見出しは接頭辞・接尾辞なしの数値3桁形式です。見出し末尾に空白区切りの補足タイトルは付けられます。
- 表示対象の分類・バージョンの重複、必須分類の欠落、`なし`と実項目の混在はエラーになります。

0.6.0〜0.9.0の正式タグ基準の履歴を整理しました。同じ表示バージョンの開発・旧Web Installer版では
一部機能が既に存在する場合があり、バージョン番号だけでその違いを完全には判定できません。
0.6.0より前の履歴は現在含んでいません。過去のタグ・Release本文は変更しません。

## JSON形式（schemaVersion 1）

```json
{
  "schemaVersion": 1,
  "firmwareVersion": "0.10.0",
  "firmwareCommit": "0123456789abcdef0123456789abcdef01234567",
  "releases": [
    {
      "version": "0.10.0",
      "features": ["追加機能の説明"],
      "improvements": []
    }
  ]
}
```

- `firmwareVersion`と`firmwareCommit`は呼び出し元が渡す`build.json`の値に固定します。
- 対象版以下の全履歴を、数値バージョンの降順に生成します。ソースの掲載順には依存しません。
- 対象版そのものの項目は必須です。未来版・Unreleasedは生成結果に含めません。
- 生成時は未来版を含む全バージョンの記載形式を検査します。
- 配信用JSONの検証は、不明なschema、不一致、重複、不正な順序、未来版、必須フィールド欠落を拒否します。
  ブラウザ側でも後続Phaseで対象範囲を検査し、将来版の内容を表示しないようにします。
- Releaseリンクはバージョンから生成できるためJSONには持ちません。
- JSONの手編集や生成物のGit登録は不要です。履歴の日時・サイトコミットを混ぜず、同じ入力から同じUTF-8バイト列を生成します。

## サイズと文字の上限

全体256 KiB、最大256バージョン、各版・各分類につき64項目、1項目1024 Unicodeコードポイントを上限とします。
制御文字・不正Unicodeを拒否し、バージョン各成分はJavaScriptで正確に比較できる整数範囲に制限します。
上限超過時は黙って省略せず、公開前のエラーとして扱います。3バージョンの初期表示制限とは別です。

## 生成・検証モジュール

`scripts/changelog.py`はネットワークアクセスや公開処理を含みません。
`generate_changes()`、`validate_changes()`、`encode_changes()`、`decode_changes()`を提供します。
デコード時はJSONの重複キーと受信バイト数も検証します。

開発・テスト用CLIは`--changelog`、`--build`、`--output`を受け取ります。
既存のタグ公開処理から自動呼び出しするため、日常運用に手動コマンドは追加しません。
このCLIだけでは、渡されたbuild情報のコミットが実際のタグやソースと一致するかは判定しません。
その照合は公開処理の`verify_source()`で行います。

## Actions・公開処理（Phase 2）

新規配布の`build.json`には次の`changes`参照情報を追加します。既存フィールドは維持します。

```json
"changes": {
  "path": "changes.json",
  "schemaVersion": 1,
  "bytes": 2652,
  "sha256": "<生成したJSONのSHA256・64文字>"
}
```

パスは`changes.json`に固定します。`changes`自体がない場合のみ旧形式として扱い、
`null`・不完全な参照・未対応schema・不正なサイズ／ハッシュはエラーにします。
新規タグ配布では参照とJSONを必須にします。

- 初回移行：旧`build.json`は履歴参照情報なしを許容。履歴対応版は参照情報を持ち、JSON欠落をエラーにします。
- main：編集途中の履歴は検査のみ。公開済みJSONを検証してそのまま保持します。
- タグ：同じコミットのCHANGELOGから生成し、build情報と同じPages成果物へ含めます。
- 文書更新：JSONを再生成せず保持し、`site/`コピーによる上書きも防ぎます。
- 旧形式ではJSONを取得せず、出力先の古い`changes.json`も削除します。現在の公開版にJSONがなくても移行できます。
- 配布前にJSONのサイズ・SHA256・schema・版・コミットを照合します。
- さらにFirmwareコミットの`CHANGELOG.md`から再生成したバイト列と比較します。main上で履歴を編集しても混入しません。
- `--validate-only`でPages成果物アップロード前に検査し、Release公開時にも同じ検査を行います。
- Release添付にも`changes.json`を含めます。過去版タグは従来どおりPagesをダウングレードしません。
- 公開順序はPages→GitHub Releaseを維持し、リンク先が一時的に未公開でも履歴本文は読めるようにします。
- Configurator：通知・Installerリンクを先に表示し、履歴失敗は履歴欄だけで扱います。

## Configurator表示（Phase 3）

既存の更新あり判定・機種判定の後、通知とInstallerリンクを先に表示します。
ブラウザから`changes.json`を別途非同期取得し、5秒のタイムアウトを設けます。
設定API・本体のステータス取得は履歴取得を待ちません。自動更新は行いません。

- `build.json.changes`の固定パス・schema・サイズ・ハッシュの形式を検査します。
- 受信ストリームを256 KiB以内かつ参照サイズ以内に制限し、UTF-8・JSONを検証します。
- schema、Firmware版・コミットの一致、公開最新版の項目、重複・項目型・文字数を検証します。
- SHA256の内容照合はActionsの配布検証で行います。ブラウザはHTTPで開く本体Configuratorでも動作するよう、Secure Context専用のWeb Cryptoに依存しません。
- 現在版より新しく公開最新版以下の項目だけを数値順で表示します。未来版は表示しません。
- 標準の`details`／`summary`で初期は折りたたみ、最大3版を用意します。
  残りは「ほかNバージョン分を表示」で展開したときに初めてDOMを生成します。
- 各版にGitHub Releaseリンクを設け、空の分類は省略します。両分類が空なら記載なしと表示します。
- 履歴本文は`textContent`で描画し、HTML・Markdownとして解釈しません。
- 旧版の参照なし、通信失敗、タイムアウト、不整合は履歴欄だけで扱い、取得失敗の案内とReleases一覧リンクを表示します。
- 配色は既存のテーマ変数を使用します。折りたたみはキーボードでも操作できます。

## 自動テスト

`node --test tests/test_firmware_update.cjs`

既存の通知テストに加え、表示範囲、数値順、3件制限、遅延展開、空分類、文字列の安全な描画、
取得失敗・サイズ超過・不整合・タイムアウト、取得中／失敗後のステータス更新継続を確認します。

`python -m unittest discover -s tests -p test_changelog.py`

`python -m unittest discover -s tests -p test_history_distribution.py`

数値順、未来版除外、対象版必須、空分類、折り返し、重複、型、版・コミット不一致、
サイズ・文字上限、決定的な出力、CLI、既存履歴の正式タグ基準を確認します。
配布テストでは旧形式移行、mainの未来版混入防止、文書更新時の完全保持、予約パス保護、
欠落・破損・不整合、実Gitコミットとの照合と公開なしの検証CLIを確認します。
既存のpackaging・release-plan・publish-releaseテストでも自動生成・タグ方針・添付を確認します。
