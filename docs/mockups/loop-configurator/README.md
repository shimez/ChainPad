# Loop対応 Configurator モック

UI/UX検討用。正式Configurator・Firmware・Engine・保存APIには組み込まない。
データはページ内のメモリだけに存在し、再読込みでサンプルへ戻る。

## 起動

リポジトリのルートから：

```powershell
& .\.venv\Scripts\python.exe docs/mockups/loop-configurator/serve.py
```

ブラウザーで **http://127.0.0.1:8778/** を開く。終了はサーバーのCtrl+C。
別ポートは `--port 8779`。Python標準ライブラリのみを使用する。
HTMLの直接オープンではなく、この専用サーバーを使う。

## 再利用しているもの

- `web/index.html`のスタイルと通常Actionの編集関数を、専用サーバーが読取り専用で抽出する。
- `web/action-ui.js`の要約・HID編集、`web/osc-addresses.js`のOSC候補、
  `web/obs-actions.js`のOBS編集をそのまま利用する。
- 通常カードの見出し・移動・削除のみ、ツリー対応のモックへ置き換える。
- OBS候補はMain／Camera／Endingなどの固定サンプル。本体やOBSへ問い合わせない。
- サーバーに書込みAPIはなく、ブラウザーからのAPI通信もCSPで禁止する。

本番ソースを書き換えずに見た目と既存編集欄を追従させるためのモック専用アダプター。
正式実装ではソース文字列の抽出ではなく、Action編集関数を共有モジュールに分離する。

## 採用した操作設計

- Input一覧はデスクトップ幅で編集領域内を追従し、その領域の末尾で止まる。
  画面高を超える場合は一覧内でスクロールできる。狭幅では上部の通常配置となる。
- ページ下部の操作説明・平坦配列プレビューはモック専用で、正式WebUIへそのまま組み込む対象ではない。
  デスクトップ幅では右側のAction編集欄と同じ列幅に配置し、Input一覧の列には広げない。

- 保存イメージは平坦なHeader／Footer配列。UI内部はID付きのツリー。
- 初期状態は展開。Loop名のボタンで個別に折りたたみ、見出しには回数・内部Action数・全体枠数を表示。
- Loop見出しの背景／≡／名前からドラッグすると、展開状態に関係なく全体が移動する。
  回数入力や削除などの操作ボタンはドラッグ開始から除外する。
- 通常Actionは≡から単独移動。
- Loopの内側末尾は、枠内の `↳ Loop … 内の末尾`。
  直後は枠外の `↓ Loop … の直後`。異なるインデント・ラベル・境界で区別する。
- 「ここまで」の終了表示はドラッグ中も含めて表示しない。
- Loop内末尾・Loop直後・Chain末尾のラベルと境界線はドラッグ中のみ表示する。
  通常時は非表示とし、挿入領域の余白は維持する。
- ドラッグ中はすべての挿入領域を可視化。有効な対象を強調し、自己／子孫への挿入を無効化。
- 折りたたまれたLoop見出しに650 msホバーすると自動展開。
  Esc、pointercancel、ウィンドウのフォーカス喪失、対象外ドロップでは配置を変更しない。
  キャンセル時はドラッグによって自動展開したLoopも元の折りたたみ状態へ戻す。
- 画面の上下端でドラッグ中の自動スクロール。
- ↑↓ボタン、≡にフォーカスして↑↓キー：同じ親の中で移動。
  別階層へのキーボード／タップ操作には「移動先…」ダイアログを使う。
- 追加は従来と同じ「＋Add Action」のみ。追加後に開く編集欄の「Action」で
  OSC／MIDI／HID／OBS／Wait／Stop Other Chains／Loopを選択する。
- Loopを選ぶと、その通常Actionを空の展開済みLoop（初期3回）へ置き換える。
  1枠からHeader／Footerの2枠へ増えるため、空きがなければLoop選択を無効化する。
- Loop内も同じ追加ボタンを使う。追加ボタンはLoopの枠内末尾に置く。
  末尾の追加用種別選択欄と専用「＋Loop」ボタンは廃止。
- 「Loop解除」は囲みの2枠だけを除去。「削除」は内部も含めて削除。
- 「直前の構造操作を戻す」は追加・移動・削除・解除前の全Chainスナップショットを復元する。
  フィールド編集専用のUndoではないため、構造操作後に行ったフィールド編集も当時の状態へ戻る。
- 折りたたみ状態・UI IDは平坦な配列に含めない。画面下のJSONで確認できる。

## モックでの仮定

- Loop回数は合計実行回数。1〜999は暫定値であり正式仕様ではない。
- 空Loopを許可。
- Header／Footerは各1枠。KEY／Encoder PushはPress・Release合計16枠、
  EncoderのCW／CCWは各8枠。繰り返し回数は枠数に影響しない。
- ネスト専用制限は設けず、枠数から自然に制限される。
- Eventをまたぐドラッグは対象外。同一Event内の任意階層へ移動できる。
- 実行シミュレーション、正式PresetへのImport／Export、本体への保存は対象外。

## 評価してほしい操作

1. **KEY 01**で、先頭のOSCを外側Loopの「内側末尾」へ移動し、次に「直後」へ戻す。
2. 展開した外側Loopの見出しをドラッグし、内部が全部付いてくるか確認する。
3. 子LoopをChain直下へ出し、別のLoop内へ入れ直す。
4. 外側Loopを折りたたみ、OSCをその見出しへホバーして展開後の途中へ挿入する。
5. 同じ操作の途中でEsc。配置と自動展開状態が元に戻るか確認する。
6. 外側Loopを自分の子Loopへ入れようとして、挿入できないことを確認する。
7. 「Loop解除」と「削除」の違い、戻す操作を試す。
8. **KEY 02**の16枠状態で追加不可となること、解除すると2枠空くことを確認する。
9. 通常Actionを編集し、OSCの候補選択やOBS操作種類の変更も試す。
10. 幅375px前後で、深いネスト・タップ移動・末尾境界を比較する。
11. 「＋Add Action」→「Action: Loop」で空のLoopに変更し、その内部にも同じ手順で子Loopを作る。
    残り1枠でActionを追加した場合、Loopへの変更が無効になることも確認する。

特に検討したい点：

- 650 msは意図せず開く／開くまで遅いのどちらに感じるか。
- 内側末尾と外側直後の距離・ラベルが十分か。
- ドラッグ中のみ表示される挿入ガイドの見やすさと、通常時の余白のバランス。
- Loop見出しの操作ボタン数、ネスト時の縦方向の長さ。
- 「移動先…」がタッチ・キーボード操作の十分な代替になるか。

## 確認結果（2026-11-17）

ブラウザーで確認：

- 初期展開・折りたたみと、平坦配列が変化しないこと。
- 展開中Loop全体のドラッグ移動。
- 実ポインター操作による「内側末尾」への移動と「Loop直後」への移動。
- ツリー操作による内外移動・子孫への移動拒否・枠数維持。
- ホバーのタイマー経路をブラウザー上でシミュレートし、約656 msで自動展開。
  Escで配置・元の折りたたみ状態を復元。
- 既存OSC／OBS編集欄からネスト内のデータを変更できること。
- OSC／MIDI／HID／OBS／Wait／Stop Other Chainsを内部に追加。
- 回数編集・0の拒否・全体削除・Loop解除・構造操作の復元。
- Press／Release合計16枠、Encoder 8枠。
- 幅375pxのiframeでサンプルと8段の空Loopにページ横スクロールなし。
  狭幅のHID／OBS編集欄も確認。
- 最終確認時のブラウザーコンソールエラーなし。
- 追加UI変更後：「＋Add Action」から編集欄が開き、Actionプルダウンで空のLoopへ
  変更できること、同じ操作で子Loopを作れることを確認。
- Wait／OBSへの従来の種別変更、OBSからLoopへの変更、変更のUndoを確認。
  16枠使用時はLoop選択を無効化し、イベントを直接発火しても超過させないことを確認。

スマートフォン実機のタッチ操作と、長距離ドラッグのスクロール速度は利用者評価が必要。
ブラウザー上でのUI確認であり、Firmware／Engineの動作検証ではない。


## 正式実装時の課題

- 現行の単一配列番号ベースの編集・フォーカス管理を、安定したUI IDとツリー対応へ移行する。
- モックの抽出アダプターを廃し、通常Actionエディターを明示的に共有する。
- ブラウザー側とFirmware側の構造検証・枠数計算を一致させる。
- 保存形式の版・互換性・回数上限・空Loop仕様を確定する。
- DnDの自動スクロール・タッチ・キーボード・スクリーンリーダーの実機検証。
- Undo範囲、削除操作の扱い、Loopの利用者向け識別名を決める。
- モックは保存・実行しないため、Engineの実行予算・キャンセル・同時実行枠は別実装となる。
